# 长视频总结采用「阶梯 + Map-Reduce 分层归并 + 压缩摘要」而非单次满载

「一键总结」目前把整篇字幕塞进单次请求，并硬截断到 5 万字符（丢尾部、无 token 感知）。我们决定：**素材预算定为 100k token**（模型统一按 256k 窗口，100k 是模型"最聪明"区间），预算内一次成稿；超出才进入**分段压缩 + 多层归并**（Map-Reduce）；多轮追问以**压缩摘要 + 近轮对话 verbatim** 为常驻上下文，原始字幕段仅在命中时间戳/章节/关键词时按需检索注入，取代每轮重发全文幕。

## 考虑过的方案

- **单次满载 + 提高截断阈值**：简单，但 5h 级字幕仍会溢出，且每轮追问重发全文幕，token 与成本随追问次数线性放大。
- **固定 90 分钟分段**：直接，但字幕密度差异极大，墙钟不是稳定单位；短/中视频也会被无谓拆段多花调用。
- **阶梯 + Map-Reduce（选定）**：预算内零成本，仅真正超长/极密才多花调用；100k 预算下绝大多数视频一次成稿，Map-Reduce 只是少数情况。

## 后果

- 新增两个模块：**预算判定**（估 token → fits/overflow → 分段计划，纯函数）与 **Map-Reduce 编排**（跑在 offscreen 文档）；`streamChat` 退化为预算内单次路径。
- 只有 Map-Reduce 路径会产生多次调用（例如 110k 字幕 → 3 段小结 + 1 次成稿 ≈ 4 次调用），故**限并发 2~3**，并在预估 ≥5 次调用时弹成本护栏；预算内（≤100k token）视频永不拆段，仍是 1 次调用。
- 追问不再重发原始字幕，token 随追问近乎常数；代价是压缩摘要有损，靠原始字幕缓存回填细节。
- 分段边界：字符预算为纲 + 章节对齐，无章节按时间戳累积。
- 默认常量（可调）：素材预算 100k token；单段输入 50k token；分段小结 10k token/段（=20% 保留，对齐 Q1 完整忠实）；归并组输入 100k token，归并仅在段数 ≥11（原始字幕 >500k token）时触发；成稿输出 ≤ 16k token；字符→token 按 `chars × 1.0`（每字符≈1 token，保守，宁可早进 Map-Reduce，溢出兜底保证正确性）。

## 修订（2026-09-06：素材预算抬至 200k 字符）

「100k 是模型最聪明区间」的保守前提按实际使用重新校准：所配模型窗口全部 ≥256k，实际视频一般不超过 7 小时（7h 中文访谈 ≈ 10-18 万字符 ≈ 9-13 万真实 token，`chars × 1.0` 估计显著偏高）。**`MATERIAL_BUDGET_CHARS` 100k → 200k 字符**（200k ≈ 256k 窗口 − 16k 输出 − 余量），其余常量不动：预算内一次成稿覆盖 7h 级长视频，15h+ 级或更小窗口模型仍走 Map-Reduce + 溢出回落链路。影响面：10-20 万字符视频的成稿与概览同转单发、长视频追问改重发全字幕、成本护栏在单发路径不触发。决策与验收记录见 `.scratch/tickets/raise-material-budget/issues/01-raise-material-budget-line.md`。
